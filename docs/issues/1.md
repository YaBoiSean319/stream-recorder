Project specification: Docker stream recorder with web controls, API, MP4 output, and storage retention

## Problem Statement

The operator needs a self-hosted Docker application that displays a live stream, records it on demand through a browser or API, produces a downloadable MP4, and manages retained recordings within a storage cap. Browser sessions must not control recording lifetime. Calendar-driven recording will be orchestrated externally through Power Automate.

Target repository: YaBoiSean319/stream-recorder. The repository was verified as empty during design; there are no existing modules, glossary, ADRs, or test conventions to reuse.

## Solution

Provide a web interface and API backed by a persistent recording service on a Linux Docker host. Start with CH91, support an editable direct stream URL, and allow exactly one recording session at a time, including its final MP4 processing. Users can preview the stream, start or stop recording, optionally set a duration, see status and storage usage, and download, delete, or pin recordings.

Recordings survive browser closure, reconnect after source interruptions, and recover after container restarts. Produce one final MP4 named from the original recording start date/time. Enforce a configurable cap over all recorder media, deleting the oldest eligible completed recordings first. Authentication is supplied by the operator through Cloudflare Access and Entra group policies.

Deliver Docker Compose configuration and a GitHub Actions workflow that builds and publishes versioned Docker images to GitHub Container Registry.

## Implementation Decisions

### Confirmed product behavior

- Initial input is a direct HLS stream discovered from the CH91 player: https://ch91.gvsit.org/hls/test.m3u8. The player page is https://ch91.gvsit.org/player.
- The source URL is editable through the interface. Snapshot the source into each admitted recording session; subsequent settings changes must not change an active session.
- One session occupies the recorder from admission through capture and MP4 processing. Reject new starts while capturing, reconnecting, recovering, or processing; enable Start again when processing completes or the session reaches a terminal error.
- Support immediate start, explicit stop, and optional duration in both interface and API.
- Duration is measured against the original wall-clock end time, including downtime. Recovery after an expired deadline finalizes captured media rather than resuming capture. A manual session has no deadline and resumes until stopped.
- Browser preview is independent of recording. Closing a browser neither stops nor cancels a session.
- Retry source connections until explicitly stopped, duration expiry, or a storage condition requires termination. Record interruption information; unavailable footage cannot be reconstructed.
- Recover persisted sessions and captured media after container restart, including interrupted finalization. A session must not be lost merely because its process disappeared.
- Produce one final MP4 containing source video and audio when available. Remux without re-encoding when codecs are MP4-compatible; use compatible re-encoding when needed.
- Name the final MP4 from the original start date/time. The exact filesystem-safe format and timezone setting are implementation choices that must be documented; recovery must preserve the original naming timestamp.
- Expose Recording, Processing, Ready, interruption/reconnection details, conversion progress, and actionable failures. Publish downloads only after the output has been successfully finalized.
- The recordings list supports download, manual delete, and pin/unpin. Manual deletion in the interface requires confirmation. Pinning prevents automatic cleanup; it does not prevent a deliberate manual deletion.
- Display filesystem capacity/free space and application media usage. A configurable media cap includes completed recordings, active capture, and conversion artifacts.
- Proactively reclaim space by deleting oldest unpinned completed recordings in original recording-start order. Do not evict active capture, media being processed, or pinned recordings. Cleanup must account for temporary conversion growth and actual filesystem free space.
- If there is insufficient reclaimable space, safely stop capture, preserve captured media as far as available space allows, and show a storage error. Do not promise final MP4 conversion when there is insufficient space to perform it.
- The operator supplies Cloudflare Access policies for browser and API access, including Entra groups and service-token access for automation. Do not add a built-in login or separate application API-key system.
- Deliver Linux Docker deployment with persistent volumes, Compose configuration, and GitHub Actions publishing versioned images to GHCR. Document installation, storage configuration, updates, recovery behavior, and external access-policy requirements.

### Proposed implementation structure and API contract

These choices make the spec implementable; they were not separate user selections and may be refined without changing the confirmed behavior.

- Use a recording service boundary that owns admission, state persistence, capture supervision, finalization, and retention. Keep the browser and HTTP layer as clients of this boundary.
- Use a durable media/state store and a media engine such as FFmpeg. Select language, framework, persistence format, and preview strategy during implementation; none is mandated by the design discussion.
- Persist the session identity, original start timestamp, snapshotted source, optional deadline, lifecycle state, media references, interruption details, pin state, and failures before relying on them for recovery.
- API operations must cover start, stop, recorder status, recording list/detail, completed MP4 download, recording deletion, pin/unpin, and settings read/update. Exact routes are to be documented rather than assumed here.
- Start returns a stable recording identifier and initial state. Concurrent or duplicate starts must never create overlapping sessions; busy conflicts must have a clear non-success response.
- Stop is safe to retry and initiates finalization of the applicable session. Prefer an optional recording identifier for stop requests, so a delayed calendar action cannot stop an unrelated later session.
- Invalid duration, malformed source settings, invalid storage caps, unknown recording identifiers, unavailable downloads, and forbidden active-media deletion must return clear errors without corrupting state.
- Recovery and cleanup must be coordinated with admission and finalization to prevent a second recorder process or deletion of media still in use.
- Graceful shutdown preserves session intent and recoverable footage; it must not be treated as an operator stop.

## Testing Decisions

The repository is empty, so no existing seams or prior test patterns are available. The proposed primary acceptance-test seam is the application's HTTP API against a controllable local HLS fixture and isolated persistent storage. This is a proposed testing decision, not a separately confirmed user preference.

Test observable behavior and stored outputs rather than internal function calls, class layout, or command construction. Use focused media inspection of resulting MP4s to verify decodability, expected tracks, and duration. Cover the recording service, persistence/recovery, media finalization, retention, and thin browser integration through this shared boundary.

Acceptance coverage:

1. Start a known local HLS stream through the API, capture footage, stop it, observe Processing then Ready, and download one playable MP4 with video/audio and the original start-time filename.
2. Start from the interface and verify browser closure does not affect recording; verify the preview works independently before, during, and after recording.
3. Race simultaneous starts and attempt a new start during processing; exactly one session is admitted and conflicting calls receive a clear busy response.
4. Verify optional duration in both controls, including duration expiry during a source outage.
5. Change the configured source while recording; the current session keeps its source and the next session uses the new source.
6. Interrupt and restore the source; previously captured footage remains, capture resumes, and interruption details are exposed.
7. Restart or forcibly terminate the container during capture; persistent state and footage recover, manual capture resumes, and timed capture retains its deadline.
8. Restart after a timed deadline has passed; captured footage is finalized without reopening capture.
9. Restart during MP4 processing; finalization recovers without duplicate final recordings or early release of session admission.
10. Exercise compatible remux and an incompatible-codec fixture requiring re-encoding; verify a playable MP4 and visible progress/errors.
11. Trigger a conversion failure; expose an actionable error and preserve recoverable source media rather than silently deleting it.
12. Fill a small test cap with completed recordings; verify eviction in oldest-first order while skipping pinned recordings.
13. Account for active and conversion artifacts in usage and capacity decisions; verify safe stop/error when only pinned or in-use media remain.
14. Verify insufficient underlying disk space is handled even if the configured cap has not been reached.
15. Pin/unpin, download, and manually delete completed recordings through the API; verify filesystem and list state agree. Verify UI deletion confirmation and that active/in-use media cannot be deleted accidentally.
16. Verify a stopped session does not resume after restart and retries of stop do not affect an unrelated later session.
17. Smoke-test a built Docker image and Compose deployment with persistent storage. Verify container replacement preserves configuration, history, pins, and media.
18. Verify the publish workflow produces documented versioned GHCR tags and the deployment references the intended image.

A short bounded live CH91 smoke test may supplement deterministic fixtures, but must not replace them. Deployment authentication verification belongs to the operator's Cloudflare Access setup; documentation must explain the application trusts that deployment boundary.

## Out of Scope

- Multiple simultaneous recordings or overlapping recording and finalization.
- An internal calendar scheduler; Power Automate manages calendar timing through the API.
- Automatic recording when a channel goes live.
- A built-in login, user management, role system, or application API-key authentication.
- Creating or administering Cloudflare Access policies, Entra groups, or Power Automate flows.
- Generic extraction of streams from arbitrary webpage URLs, YouTube, or Twitch.
- Recording footage from before Start, replay buffers, or reconstructing footage missed during outages.
- Video editing, clipping, caption generation, or uploads to other platforms.
- A multi-stream catalog or multi-host recorder cluster.

## Further Notes

- The user confirmed the final design on 2026-10-13 and requested specification publication rather than implementation in this step.
- A bounded live probe during design observed H.264 video at 1920×1080, reported 60 fps, and AAC stereo audio at 48 kHz. The HLS playlist used MPEG-TS segments and was accessible without authentication from the inspection environment. These are observations, not guarantees about future source behavior.
- Underlying HLS segment boundaries mean exact frame-level start and stop timing is not guaranteed. Document measured behavior.
- The repository is public. Keep deployment-specific credentials and service tokens out of repository contents and example configuration.
- Concrete defaults for the storage cap, cleanup headroom, filename timezone, exposed host port, and deployment volume locations should be documented during implementation. They were not specified by the user.
- This issue is the project specification, not a claim that the application, image, authentication policies, or calendar integration have already been built.
