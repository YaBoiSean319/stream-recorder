Handle incompatible media and conversion failures

## Parent

Project specification: #1

## What to build

Extend the complete recording path to produce compatible MP4 output when the source cannot be directly remuxed, while showing processing progress and preserving recoverable media on failure.

Implement this as an end-to-end slice, including persistent state, API, interface, and observable tests where applicable. Parent specification #1 governs the confirmed requirements; do not close or edit it.

## Acceptance criteria

- [ ] Keep compatible remuxing as the default quality-preserving path; re-encode incompatible sources into documented MP4-compatible video/audio formats when needed.
- [ ] Each successful session still yields one validated final MP4 with the original start-time filename.
- [ ] UI and API expose meaningful conversion progress and actionable failure details; do not present a partial output as Ready.
- [ ] New recording admission remains blocked throughout conversion, including fallback conversion, and releases only at a terminal state.
- [ ] Failure preserves recoverable captured media and avoids deleting the only usable source footage.
- [ ] Deterministic tests cover compatible remux, incompatible input requiring re-encoding, conversion failure, playable output/track inspection, and admission while processing.
